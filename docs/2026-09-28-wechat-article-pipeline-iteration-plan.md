# 公众号文章链路迭代规划

> 制定时间：2026-09-28  
> 状态：规划，尚未按本文实施  
> 范围：05:00 素材准备、06:00 公众号文章创建、异步草稿发布，以及 10:00 案例线对文章选题的影响。

## 1. 基线与目标

当前代码以 `master@7f35297` 加本地未提交修改为基线。当前工作区已加入 DeepSeek 直连、文章/案例主题记录隔离、增量选题判断、质量拒绝退出码、任务结果计数与本地连续失败告警。这些修改尚未提交或部署。此前本地烟测覆盖了语法、主题隔离、告警状态、模拟 DeepSeek 请求和规则质量闸门；完整 pytest 套件因当前启动器失效且环境缺少 pytest 未运行，真实 DeepSeek 和微信接口也未验证。

`README.md` 与脚本描述的运行次序是：`run_all.sh` 采集 → `run_daily_full.sh` 创建公众号文章 → `publish_worker.py` 消费草稿队列 → `run_daily_case.sh` 创建案例。实际定时器配置与最近几天的线上日志尚未核实，因此这里把脚本次序视为**设计基线**，不视为线上执行证明。用户反馈的 OpenRouter 401、素材池薄弱及连续失败，是排查线索；其中近期失败次数和占比仍需运行记录确认。

本轮迭代的目标：

1. 每次 06:00 执行都能明确回答：输入了多少素材、为什么选中或拒绝、写成了几篇合格终稿、是否入队、是否创建微信草稿。
2. 目标仍为每日两篇；若仅有一篇达到质量标准，产出该篇并标记为部分完成；零篇合格时明确失败和原因，不强行放宽质量门槛。
3. 只有**润色后的终稿**通过检查，才将其来源和主题记为已使用并进入发布队列。
4. 文章与案例的主题多样性各自判断，同一来源 URL 仍跨类型去重。
5. 可重跑、可定位、可回退；本地验证、真实模型调用、真实微信草稿创建分别记录证据。

## 2. 当前链路与已确认的设计缺口

| 环节 | 当前行为与代码依据 | 需要解决的问题 |
| --- | --- | --- |
| 素材供给 | `content_platform/runtime.py` 采集并缓存；文章池在 `content_platform/datasets/article_pool.py` 主要按综合分 `>=0.65`、正文 `>=800` 字和近期 cluster 过滤 | 有足够字数与综合分的纯观点材料仍可能进入写作；素材池变薄时，失败被推迟到文章生成后 |
| 选题 | `content_platform/business/daily_article/topic_planner.py` 先重排前 8 条，再有界补看候选；按 URL、标题、近期文章主题去重 | “独立增量”目前主要由一次模型回答决定；模型不可用时会放行，需记录判断依据与降级状态 |
| 写作与质量 | `write_article.py` 在润色前评估质量；通过后立即写主题记录和已用来源，然后继续润色、配图与入队 | 质量结果不代表最终稿；后续步骤失败时，来源可能已被占用 |
| 质量证据 | `check_article_quality()` 将数字、证据词及来源元数据作为规则信号；`QUALITY_LLM_JUDGE` 默认未开启 | 规则可证明“有信号”，不能证明具体论断受到来源支持；需要终稿级来源核对 |
| 任务状态 | `content_platform/job_state.py` 固定使用任务类型、日期和 `_001` 组成任务 ID；`runtime.py` 多篇 writer 日志共用文件名 | 同日重跑覆盖历史，后写的文章日志覆盖前一篇；异常退出可能绕过健康状态写入 |
| 发布与告警 | `publish_worker.py` 有队列重试；`content_platform/alerts.py` 存本地连续失败状态并打印告警 | 告警尚未触达负责人；编排层异常和 daemon 外层错误缺少统一终态记录 |
| 案例多样性 | `content_platform/recent_topics.py` 分开保存文章和案例；案例记录的 `cluster_ids` 为空，而 `case_pool.py` 主要用该字段排除近期 cluster | 案例线能按来源 URL 去重，但案例主题历史尚未真正用于同类主题判断 |

## 3. 迭代顺序

一次只推进一个里程碑。每个里程碑只修改表内范围，完成其验收后再启动下一个；估时是开发量级，基于当前代码，不含外部接口故障排查时间。

| 里程碑 | 优先级 / 估时 | 交付物 | 完成条件 |
| --- | --- | --- | --- |
| M0 形成可信基线 | P0 / 0.5–1 天 | 运行记录盘点、隔离的测试环境、当前行为基线 | 能区分素材不足、模型失败、质量拒绝、入队失败、微信发布失败；测试入口可运行，不改线上数据 |
| M1 终稿验收与提交时序 | P0 / 1–2 天 | 质量门移到润色后；失败显式退出；通过后再提交已用主题、URL 和队列记录 | 润色失败或终稿拒绝时无新增“已用”记录、无入队；合格终稿入队一次 |
| M2 素材质量与候选补选 | P0 / 1–2 天 | 证据质量进入候选选择；不足时从合格候选继续补选；区分 0、1、2 篇结果 | 纯观点不因长度和综合分被优先写作；有替补时可补选；无合格材料时明确报告不足 |
| M3 运行追踪与告警闭环 | P0 / 1–2 天 | 每次运行独立 ID、每篇独立日志、异常终态、连续失败和恢复通知 | 同日重跑互不覆盖；任意失败路径都有终态和阶段原因；连续失败只告警一次、恢复可见 |
| M4 案例与路径一致性 | P1 / 1 天 | 案例专用主题判断；读取历史时显式传入 `workspace_dir` | 相同案例主题可识别独立增量；案例不占文章窗口；不同工作区不会串用历史 |
| M5 小范围真实验收 | P0 发布门 / 1–2 次运行 | 真实 DeepSeek、06:00 作业、微信草稿的分层证据和回退记录 | 真实接口、排程、队列及草稿结果分别有可复核记录；异常时切回人工审稿流程 |

### M0 — 先让失败可复现

- 读取可获得的最近运行日志、`platform/jobs`、数据集、`queue/`，逐次列出素材量、候选量、写作退出码与草稿结果。缺失的历史证据明确记“未知”，不以用户描述推算失败率。
- 恢复隔离的 pytest 运行入口；沿用仓库依赖约定，不为验证改动线上 Python 或凭据。固定文章池、主题判断、写作退出码、队列幂等与任务状态的离线样例。
- 输出一张基线漏斗：采集数 → 可评分数 → 文章候选数 → 选中数 → 终稿合格数 → 入队数 → 草稿成功数。按每天和失败原因保留原始路径。

### M1 — 先修正“什么时候算写成文章”

- 将润色视为写作的一部分。润色非零退出、超时或最终文件缺失，应使 writer 非零退出，并保留草稿及错误报告以供人工修订。
- 对润色后的 `article.md` 重新执行质量门。来源核对至少要求终稿中可以定位引用或来源位置；“素材元数据里有 URL”不能单独等同于文中论断可追溯。语义复核需要明确启用条件、成本预算与失败状态。
- 最终质量通过且终稿保存成功后，再记录文章主题、标记来源已用、入队。三个写入动作采用稳定的文章 ID 做幂等检查；中途失败可安全重试，不能重复入队。
- 验收使用四类离线场景：润色成功、润色失败、润色后质量下降、队列写入失败。每类检查退出码、终稿、主题账本、URL 状态和队列状态。

### M2 — 让好素材优先，素材不足时及时说明

- 在文章候选中引入可解释的证据字段：原始来源、可核实事实/数据/实施细节、素材正文完整度及评分置信度。先用于排序与诊断，再根据 M0 基线决定最低门槛；避免一次性加硬阈值把池子压空。
- 选题层区分“同一原始素材”“同一论点复述”和“同一大方向但有独立增量”，保存判断理由、参考历史记录与模型是否可用。模型失效时保留确定性的 URL/标题去重，并把语义判断标为未验证。
- 当候选在 URL、主题或证据检查中被拒绝时，继续从已评分的合格候选中补选，限制扫描数量和模型调用预算。当天仍不足时允许使用新鲜度合格的跨日素材；不把低质量素材当作保底稿。
- `article_count=2` 的结果语义明确为：2 篇合格 `success`、1 篇合格 `partial`、0 篇合格 `failed`；每个状态都附拒绝原因计数。

### M3 — 每次运行都留下一份独立、完整的证据

- `job_id` 增加运行时间或随机后缀；同日多次运行写各自的 `job.json`，提供日期级索引。writer 日志使用文章序号或稳定文章 ID 命名。
- 编排入口统一捕获阶段异常，在 `finally` 中写终态和健康结果。将“流程执行失败”“候选不足”“质量不合格”“外部服务失败”分开统计。
- 本地告警继续保留；接入飞书、邮件等外部渠道前先确定接收目标及凭据来源。通知只包含任务、阶段、连续次数、运行 ID 和日志路径，不包含密钥、全文或素材正文。
- 验收覆盖两次连续失败、混合成功/失败、恢复、重复触发与进程异常退出；确认调度命令返回码与记录状态一致。

### M4 — 保持文章与案例的边界清楚

- 案例记录写入可比较的 cluster 或主题标识，并仅与案例历史做多样性判断；跨类型仅共享规范化来源 URL 与内容哈希去重。
- 将主题账本、文章池、选题器的工作区根路径改为显式参数；保留旧混合账本的只读兼容，确认过渡窗口结束后再决定是否归档，不能直接删历史。

### M5 — 分层验证与发布

1. **离线**：先跑与改动相关的池子、选题、质量、状态和队列检查，再跑模块级测试；记录数量和失败详情。mock 成功只证明本地行为。
2. **真实 DeepSeek**：用受限的一次请求验证模型 ID、认证、返回内容及错误分类，记录请求成本与耗时；不打印凭据。
3. **真实微信草稿**：使用明确指定的测试文章创建草稿，核对队列 `done` 状态与返回的 `media_id`。这一步是外部写入，应在目标账号和测试文章确定后执行。
4. **排程观察**：核对机器上的真实定时任务，再观察至少连续数次 05:00/06:00/10:00/worker 执行。每天统计漏斗、总耗时、失败原因、重复素材与告警到达情况。没有实际记录，不宣称线上恢复。

## 4. 通过标准与回退

首批观察窗口建议为连续 7 天，最终目标按 M0 基线校准。最低通过条件：零个静默成功、零个被拒绝终稿入队、零个同一文章重复入队、每次失败都有运行 ID 和阶段原因；遇到不足两篇时准确呈现 `partial` 或 `failed`。真实模型、排程、微信草稿三种状态分别验收。

每个里程碑保留独立改动记录和回退说明。上线前保存当前代码修订、相关环境变量名称与队列/账本路径；回退只针对本里程碑改动，不清理历史产物或重置现有工作区。若终稿门或调度出现意外，暂停自动入队，保留生成稿交人工审核；查清状态后再恢复，不以关闭质量检查换取表面成功率。

当前工作区还存在原有的 `assets/placeholder.jpg` 删除状态以及未跟踪缓存目录；它们不属于本文任务，后续实施与提交需继续保留并单独核对。

## 5. 下一步的单一实施单元

先完成 **M0 基线与测试入口**，然后只实施 **M1 终稿验收与提交时序**。M1 验收通过前，不同步调整素材分数阈值、案例策略或生产排程。这样可以先确定“成功”确实对应一篇可发布的终稿，再用可靠的失败漏斗决定素材策略。
